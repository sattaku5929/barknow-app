## 2026-10-24 実セッションのAPI認証テスト

テスト環境: PR #147（PR #146をベースにした**一時的な検証専用Preview**）。
テスト対象: `GET /api/google-calendar/status`（読み取り専用）。対象外のAPI全般を検証した結果ではない。

| ケース | 期待するHTTP | 実測 | 判定 |
| --- | --- | --- | --- |
| Admin + AAL2 | 200 | 200 | PASS |
| Admin + AAL1（Authenticator前の実セッション） | 401 | 401 | PASS |
| Coach + AAL1 | 200 | 200 | PASS |
| Owner + AAL1 | 401 | 401 | PASS |
| 無効なBearerトークン | 401 | 401 | PASS |

結果は利用者が画面上で確認、スクリーンショットを提供。パスワード、TOTP秘密情報、トークンは台帳に保存していない。
検証の途中でPreview側の `SUPABASE_SERVICE_ROLE_KEY` などの環境変数不足を特定し、Preview再デプロイ後にAAL2/200を確認した。

## 残課題と次の安全な作業

1. **本番スモークテスト:** 本番で管理者がMFA後ログインでき、対象APIやGoogleカレンダー主要導線が機能することを非破壊的に確認する。
2. **mainマージ後CI:** PR #146マージ前には `fresh-db` / `admin-aal2-api` が成功。マージ後 `fresh-db` はSUCCESS、Supabase PreviewチェックはSKIPPED（2026-10-24確認）。
3. **Previewの機密鍵を整理:** 本番SupabaseのService Role Keyを共有している場合、利用者が2026-10-24にPreview適用解除を報告。Vercel設定の直接確認は権限不足（403）で未検証。既存Previewデプロイに旧環境変数のスナップショットが残り得るため、古いデプロイのアクセス制御・削除も点検する。Productionの適用が維持されていることも設定画面で確認する。
4. **検証用PR #147の整理:** 検証結果記録後にPR #147をマージせずクローズ済み。検証用ページはmainには含まれない。
5. **DB認可の段階的強化:** PR #140はDBスナップショット、既存RLS/RPC差分、リカバリー手段、AAL1/AAL2実接続のテストを行ってから別途承認・適用する。
6. **セキュリティ全体監査:** 他のAPI、RLS、Storage、メール認証、復旧手段、秘密鍵の権限範囲とローテーション、監査ログを別途評価。

## 資料に転用できる説明例

> WanToneでは、Supabaseによる会員認証とユーザー権限管理を採用し、管理者向けの一部の重要なAPIには、認証アプリを使った2段階認証の完了を必須としています。管理者・コーチ・飼い主それぞれの権限に応じてAPIのアクセス可否を判定し、実際の認証セッションを使ったアクセス許可・拒否の検証を行っています。セキュリティ対策は段階的に拡充しており、データベース層の追加強化や運用監査は継続課題です。

避ける表現: 「全通信・全DBがAAL2で守られている」「第三者監査済」「ISMS/SOC 2認証取得」「脆弱性ゼロ」「完全なセキュリティ」。
